## 1. Executive Summary & Operational Scope

This Standard Operating Handbook defines the operational protocols, cryptographic standards, dual-custody governance, and append-only transparency log auditing requirements for the Enterprise Autonomous Operation & Regulatory Compliance System (EAORCS) Root and Intermediate Certification Authorities (CAs).

The primary objective of EAORCS Trust Operations is to guarantee zero-trust cryptographic assurance across all platform attestations, software identity passports, and cross-domain communications.

---

## 2. Certificate Authority Architecture & Trust Hierarchy

The EAORCS Trust Fabric employs a multi-tiered hierarchical Certification Authority model designed to isolate high-value root credentials from operational runtime systems:

```
                      +------------------------------------------+
                      |       EAORCS Offline Root CA             |
                      |  (RSA-4096 / M-of-N Threshold Secret)    |
                      +--------------------+---------------------+
                                           |
                                           v
                      +--------------------+---------------------+
                      |   EAORCS Intermediate Operations CA      |
                      |  (RSA-4096 / EC-P384 Operational Keys)   |
                      +--------------------+---------------------+
                                           |
           +-------------------------------+-------------------------------+
           |                               |                               |
           v                               v                               v
+----------+----------+       +------------+----------+       +------------+----------+
|  Software Passport   |       |  Federated Node Trust    |       |  Telemetry & Audit    |
|  Issuance Authority |       |  Attestation Authority   |       |  Log Signer Authority |
+---------------------+       +-----------------------+       +-----------------------+
```

1. **Offline Root CA**: Holds the master trust anchor. Private key is never stored online as a single file; it is split into $M$-of-$N$ threshold secret shares distributed among human custodians.
2. **Intermediate Operations CAs**: Issue short-lived software identity attestations, node identity certificates, and audit bundle signatures.
3. **Cryptographic Transparency Log**: Records all CA lifecycle events (key generation, certificate issuance, key rotation, revocation) in an immutable append-only hash chain backed by Merkle inclusion proofs.

## 3. Cryptographic Transparency Log Engine (`CATransparencyLogEngine`)

### 3.1 Hash-Chain Ledger Mechanics
All Certificate Authority events are recorded sequentially in the `CATransparencyLogEngine`. Each entry $E_i$ contains:
- **Index ($i$)**: Zero-based sequential integer ($0, 1, 2 \dots$).
- **Timestamp**: ISO 8601 UTC timestamp.
- **Event Type**: Defined operational event (`ROOT_CA_INITIALIZED`, `KEY_GENERATED`, `CERTIFICATE_ISSUED`, `CERTIFICATE_REVOKED`, `KEY_ROTATED`).
- **Payload**: JSON metadata detailing the operation.
- **Previous Hash ($H_{i-1}$)**: SHA-256 hash of entry $E_{i-1}$ (Genesis entry $E_0$ uses 64 zeros).
- **Entry Hash ($H_i$)**: Calculated as:
  $$H_i = \text{SHA-256}(i \mathbin{\Vert} \text{Timestamp} \mathbin{\Vert} \text{EventType} \mathbin{\Vert} H_{i-1} \mathbin{\Vert} \text{JSON}(Payload))$$
- **Digital Signature**: Optional RSA/ECDSA signature generated by the CA Log Signing Authority.

### 3.2 RFC 6962 Merkle Tree Audit Verification
To allow external auditors to verify log inclusion without scanning the entire history, `CATransparencyLogEngine` builds a binary Merkle tree over all entry hashes adhering to RFC 6962 domain separation rules:
- **Leaf Node Hash**: $L_i = \text{SHA-256}(0\text{x}00 \mathbin{\Vert} H_i)$
- **Internal Node Hash**: $N = \text{SHA-256}(0\text{x}01 \mathbin{\Vert} \text{Child}_{\text{left}} \mathbin{\Vert} \text{Child}_{\text{right}})$

#### Inclusion Proof Verification Procedure:
1. Obtain the target entry hash $H_k$ and the recorded Merkle Root $R$.
2. Request the logarithmic Merkle inclusion proof array $P = [s_1, s_2, \dots, s_d]$ where each step $s_j = (\text{position}, \text{hash})$.
3. Reconstruct the root candidate $R'$ starting from $L_k = \text{SHA-256}(0\text{x}00 \mathbin{\Vert} H_k)$:
   $$R_{j} = \begin{cases} 
   \text{SHA-256}(0\text{x}01 \mathbin{\Vert} s_j.\text{hash} \mathbin{\Vert} R_{j-1}) & \text{if } s_j.\text{position} = \text{'left'} \\
   \text{SHA-256}(0\text{x}01 \mathbin{\Vert} R_{j-1} \mathbin{\Vert} s_j.\text{hash}) & \text{if } s_j.\text{position} = \text{'right'}
   \end{cases}$$
4. Assert $R' == R$. If match succeeds, the entry is proven to exist immutably in the log.

## 4. Key Ceremony Governance & Quorum Protocols (`KeyCeremonyOrchestrator`)

### 4.1 Dual-Custody Governance Matrix
All Root and Intermediate CA key generation and key rotation operations require multi-party dual-custody authorization. Single-person key control is strictly prohibited by policy.

| Custodian Role | Required Minimum | Responsibilities |
| :--- | :---: | :--- |
| `SECURITY_OFFICER` | 1 | Authorization of security policy, identity verification of custodians. |
| `PRIMARY_CUSTODIAN` | 1 | Physical/Cryptographic activation of primary threshold key share. |
| `SECONDARY_CUSTODIAN` | 1 | Secondary key share custody and redundancy verification. |
| `GOVERNANCE_WITNESS` | 1 | Independent observation of key ceremony steps and timeline recording. |
| `AUDITOR` | 1 | Post-ceremony verification of transparency log entries and signatures. |

### 4.2 $M$-of-$N$ Threshold Secret Sharing Protocol
CA Private Keys are protected using Shamir's Secret Sharing scheme evaluated byte-by-byte over Galois Field $GF(256)$ with primitive polynomial $P(x) = x^8 + x^4 + x^3 + x + 1$ (`0x11b`).
- **Threshold ($M$)**: Minimum number of shares required to reconstruct the private key (Default: 3).
- **Total Shares ($N$)**: Total shares generated and distributed (Default: 5).
- **Polynomial**: For each byte $k$ of the private key secret $S$, a polynomial of degree $M-1$ is constructed:
  $$f_k(x) = S_k \oplus a_1 x \oplus a_2 x^2 \oplus \dots \oplus a_{M-1} x^{M-1}$$
- **Share Generation**: Share $i$ receives $(i, f_k(i))$ for $i = 1 \dots N$.
- **Reconstruction**: Any $M$ custodians present their shares $(x_i, y_i)$, and Lagrange Interpolation over $GF(256)$ at $x=0$ reconstructs the exact secret:
  $$S_k = \bigoplus_{i=1}^{M} \left( y_{i,k} \otimes \prod_{j \ne i} \frac{x_j}{x_i \oplus x_j} \right)$$

### 4.3 Key Ceremony Step-by-Step Operating Procedure

#### Step 1: Ceremony Initiation
The Ceremony Master initializes the workflow via `KeyCeremonyOrchestrator.initiateCeremony()`:
```javascript
orchestrator.initiateCeremony('CEREMONY-ROOT-2026', {
  thresholdM: 3,
  totalN: 5,
  keyType: 'RSA-4096',
  caType: 'ROOT',
  caName: 'EAORCS Root Certification Authority'
});
```

#### Step 2: Custodian Registration & Verification
All $N$ custodians present enterprise credentials and public keys to be registered:
```javascript
orchestrator.registerCustodian('cust-1', 'Alice Security', CustodianRole.SECURITY_OFFICER);
orchestrator.registerCustodian('cust-2', 'Bob Primary', CustodianRole.PRIMARY_CUSTODIAN);
// ... register remaining custodians up to N
```

#### Step 3: Dual-Custody Check-In & Quorum Validation
Custodians present single-use authentication proofs to check in:
```javascript
orchestrator.checkInCustodian('cust-1', authProof1);
orchestrator.checkInCustodian('cust-2', authProof2);
orchestrator.checkInCustodian('cust-3', authProof3);

const quorumStatus = orchestrator.verifyQuorum();
// Must satisfy: count >= M AND includes SECURITY_OFFICER AND includes PRIMARY_CUSTODIAN
```

#### Step 4: Key Generation & Secret Splitting
Once `QUORUM_REACHED`, key generation is executed:
```javascript
const keyGenResult = orchestrator.executeKeyGeneration();
```
1. High-entropy RSA-4096 or EC-P384 key pair is generated.
2. Private Key PEM buffer is split into $N$ Shamir secret shares.
3. Shares are encrypted with individual custodian public keys and distributed.
4. Event `KEY_GENERATED` is logged to `CATransparencyLogEngine`.

#### Step 5: Finalization & Sealed Storage
The ceremony is completed via `orchestrator.completeCeremony()`. Private key memory buffers are immediately overwritten and garbage-collected. Custodians store their secret share in air-gapped hardware security modules (HSMs) or smart cards.

## 5. Key Rotation State Machine & Lifecycle Management

Root CA keys undergo scheduled rotation every 36 months; Intermediate CA keys undergo scheduled rotation every 12 months.

```
       +--------------+        initiateKeyRotation()        +--------------------+
       |  COMPLETED   | ----------------------------------> | ROTATION_INITIATED |
       +--------------+                                     +---------+----------+
              ^                                                       |
              |                                                       | checkInCustodian()
              | executeKeyRotation()                                  v
       +------+-------------------+                         +---------+----------+
       | ROTATION_COMPLETED       | <---------------------- | ROTATION_QUORUM    |
       +--------------------------+                         +--------------------+
```

1. **Rotation Initiation**: State transitions to `ROTATION_INITIATED`.
2. **Re-Authorization Quorum**: Custodians re-authenticate and check in. State moves to `ROTATION_QUORUM_REACHED`.
3. **Replacement Key Generation**: A new RSA-4096 / EC-P384 key pair is generated and split into new custodian shares.
4. **Transparency Log Linkage**: Event `KEY_ROTATED` is logged containing `previousKeyId`, `previousFingerprint`, `newKeyId`, and `newFingerprint`, preserving cryptographic traceability across key transitions.

## 6. Certificate Revocation & Emergency Key Compromise

### 6.1 Emergency Revocation Protocol
In the event of key compromise or custodian breach:
1. Any `SECURITY_OFFICER` initiates emergency revocation.
2. Certificate serial number is appended to `CATransparencyLogEngine` with event `CERTIFICATE_REVOKED` and reason `KEY_COMPROMISE`.
3. An updated Certificate Revocation List (CRL) is published immediately across all platform endpoints.
